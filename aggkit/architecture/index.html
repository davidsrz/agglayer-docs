    Architecture¶

    AggKit follows a modular, component-based architecture that enables flexible deployment and scaling based on specific network requirements.

    System Overview¶

    graph TB
    subgraph "AggKit Node"

        L1S[L1InfoTreeSync]
        BRS[BridgeSync]
        LGS[LastGERSync]
    end

    subgraph "External Systems"

        L1[L1 Network]
        L2[L2 Network]

    Core Components¶

    AggSender¶

    The AggSender is responsible for building and submitting certificates to the AggLayer containing bridge state proofs.

    Key Functions: - Certificate generation from bridge state - Proof aggregation and validation - Submission to AggLayer via gRPC - Status tracking and retry logic

    Architecture: 

    graph LR
    subgraph "AggSender"
        BN[Block Notifier]
        EN[Epoch Notifier]
        PC[Proof Client]
        CS[Certificate Store]
        SC[Status Checker]
    end

    BN --> EN
    EN --> PC
    PC --> CS
    CS --> SC
    SC --> AggLayer[AggLayer]

    Database Schema: - certificates - Certificate metadata and status - certificate_items - Individual certificate components - sync_info - Synchronization state tracking

    AggOracle¶

    The AggOracle propagates the Global Exit Root (GER) from L1 to L2 chains, enabling cross-chain bridging.

    Key Functions: - Monitor L1 for GER updates - Calculate new GER values - Submit GER updates to L2 networks - Handle transaction management and retries

    Flow: 

    sequenceDiagram
    participant L1 as L1 Network
    participant AO as AggOracle
    participant L2 as L2 Network

    L1->>AO: GER Update Event
    AO->>AO: Calculate New GER
    AO->>L2: Submit GER Transaction
    L2->>AO: Transaction Receipt
    AO->>AO: Update Status

    Bridge Service¶

    The Bridge Service provides a REST API for bridge operations and queries.

    Endpoints: - GET /bridge/info - Bridge configuration information - GET /bridge/status - Current bridge status - POST /bridge/deposit - Initiate bridge deposit - GET /bridge/claim/{depositCount} - Get claim information - GET /bridge/merkle-proof - Generate Merkle proofs

    API Architecture: 

    graph TB
    Client[Client Application]
    API[REST API Layer]
    BL[Business Logic]
    DB[(Database)]
    BC[Blockchain Client]

    Client --> API
    API --> BL
    BL --> DB
    BL --> BC

    L1InfoTreeSync¶

    The L1InfoTreeSync synchronizes L1 state information and maintains Merkle trees.

    Key Functions: - Monitor L1 for relevant events - Build and maintain L1 info trees - Provide tree data for certificate generation - Handle blockchain reorganizations

    Data Structures: - L1 Info Tree - Merkle tree of L1 state - Rollup Exit Tree - Tree of rollup exit information - Index mapping for efficient lookups

    BridgeSync¶

    The BridgeSync monitors bridge events from both L1 and L2 networks.

    Event Types: - BridgeEvent - Bridge deposits and withdrawals - ClaimEvent - Claim transactions - UpdateL1InfoTree - L1 info tree updates

    Processing Flow: 

    graph TD
    Monitor[Event Monitor]
    Queue[Event Queue]
    Processor[Event Processor]
    Validator[Event Validator]
    Store[Data Store]

    Monitor --> Queue
    Queue --> Processor
    Processor --> Validator
    Validator --> Store

    LastGERSync¶

    The LastGERSync tracks the latest Global Exit Root injected on L2.

    Key Functions: - Monitor L2 for GER injection events - Track latest GER values - Provide GER information to other components - Handle different L2 network types (Polygon, Optimism)

    Database Schema¶

    AggKit uses SQLite as the default database with the following key tables:

    Core Tables¶

    -- Certificate tracking
CREATE TABLE certificates (
    id INTEGER PRIMARY KEY,
    network_id INTEGER,
    height INTEGER,
    status TEXT,
    certificate_data BLOB,
    created_at TIMESTAMP
);

-- Bridge events
CREATE TABLE bridge_events (
    id INTEGER PRIMARY KEY,
    network_id INTEGER,
    block_number INTEGER,
    event_type TEXT,
    event_data TEXT,
    processed_at TIMESTAMP
);

-- L1 info tree data
CREATE TABLE l1_info_tree (
    id INTEGER PRIMARY KEY,
    block_number INTEGER,
    timestamp INTEGER,
    tree_root TEXT,
    tree_size INTEGER
);

    Configuration Architecture¶

    AggKit uses a hierarchical configuration system:

    Default Values → Config Files → Environment Variables → CLI Flags

    Configuration Sources: 1. Default Config (config/default.go) - Base configuration values 2. TOML Files - Network-specific configurations 3. Environment Variables - Runtime overrides 4. CLI Flags - Command-line overrides

    Example Configuration Structure: 

    [aggsender]
enabled = true
aggregate_proof_service_rpc_url = "http://localhost:50061"

[aggoracle]
enabled = true
l1_rpc_url = "http://localhost:8545"
l2_rpc_url = "http://localhost:8546"

[bridge_service]
enabled = true
port = 8080

    Component Communication¶

    Inter-Component Communication¶

    Components communicate through:

    1. Shared Database - Primary data sharing mechanism
    2. Event System - Pub/sub for real-time updates
    3. Direct Interfaces - Go interfaces for tight coupling where needed

    External Communication¶

    • gRPC - Communication with AggLayer
    • JSON-RPC - Blockchain network communication
    • REST API - Client-facing interface
    • WebSocket - Real-time event streaming (optional)

    Scalability Considerations¶

    Horizontal Scaling¶

    • Component Distribution - Run components on separate machines
    • Database Sharding - Split data across multiple databases
    • Load Balancing - Distribute API requests

    Performance Optimization¶

    • Connection Pooling - Reuse blockchain connections
    • Batch Processing - Group operations for efficiency
    • Caching - Cache frequently accessed data
    • Async Processing - Non-blocking operations where possible

    Security Architecture¶

    Key Management¶

    • Hardware Security Modules (HSM) support
    • Key derivation from secure seeds
    • Role-based access to signing operations

    Network Security¶

    • TLS encryption for all external communication
    • Authentication via signed requests
    • Rate limiting to prevent abuse
    • Input validation for all external data

    Data Integrity¶

    • Cryptographic proofs for all state transitions
    • Merkle trees for efficient verification
    • Database constraints to prevent invalid states
    • Audit logging for all operations

    Monitoring and Observability¶

    Metrics¶

    AggKit exposes Prometheus metrics for: - Certificate generation rates - Bridge event processing times - Database query performance - Network connection status

    Logging¶

    Structured logging with: - Component identification - Correlation IDs for request tracking - Error categorization - Performance metrics

    Health Checks¶

    Built-in health check endpoints: - Component status - Database connectivity - Network connectivity - Resource utilization

    Error Handling¶

    Retry Logic¶

    • Exponential backoff for transient errors
    • Circuit breaker pattern for failing services
    • Dead letter queues for unprocessable events

    Failure Recovery¶

    • Graceful degradation when components fail
    • State recovery after restarts
    • Data consistency checks and repairs
    • Manual intervention procedures for critical failures
